Today we are shipping **Probe 2.0**, the biggest upgrade to our
web-testing agent since launch. The headline change: when Probe finds a
bug, it now **files the ticket for you**, in Linear, Jira, or GitHub,
with a clear title, reproduction steps, and the failing screenshot
attached. No more copy-pasting a run summary into your tracker.

Underneath that, 2.0 is faster, runs tests in parallel, and finally
knows the difference between a real bug and a flaky test. This post
covers what changed, where the gains come from, and what you need to do
to upgrade (spoiler: nothing).

## What's new

### Agents file their own tickets

This is the change everyone asked for. Before 2.0, Probe drove the
browser, found the bug, and handed you a report. You still had to open
your tracker and write the ticket. Now Probe does it: when a run records
a failure, the agent opens a ticket in the connected tool with a
descriptive title, the exact steps it took, the expected versus actual
result, console errors, and the screenshot at the moment of failure.
Duplicate detection means a bug that fails on three releases in a row
becomes one ticket with three comments, not three noisy tickets.

### Parallel test runs

A Probe 2.0 workspace spins up multiple isolated browser sessions at
once. A suite that used to walk twelve flows one after another now runs
them across parallel agents and finishes in a fraction of the time.
Each session is fully isolated, so a login in one flow never leaks into
another.

### Flake-aware retries

The single most annoying thing about automated testing is a test that
fails for no reason. Probe 2.0 carries an explicit confidence signal
and, on a failure, re-runs the exact same steps in a fresh session
before deciding. A failure that does not reproduce is labelled a
**flake** and kept out of your ticket tracker. A failure that
reproduces is filed. Noise goes down, trust goes up.

### Faster browser perception

The vision backbone that reads each page is new. It identifies
buttons, inputs, and small UI controls in roughly a third of the time,
which is what makes parallel runs practical without a huge cost
increase.

## Where the gains come from

The speed comes from two places. Parallelism is the obvious one. The
less obvious one is that the previous bottleneck was never the agent's
reasoning, it was the number of times it re-read the page just to be
sure something had changed. The new perception backbone is fast and
confident enough that Probe can skip most of those redundant reads.

The reliability gains come from flake-aware retries. A large share of
pre-2.0 tickets were not bugs at all, they were timing issues, slow
networks, and animations that had not settled. Re-running the exact
failing steps in a clean session before filing anything removes that
whole category of noise.

## What you need to do

Nothing. Every Probe workspace is on 2.0 as of today. Existing test
plans run unchanged. To turn on automatic ticket filing, connect Linear,
Jira, or GitHub in your workspace Integrations tab and pick the project
each agent should file into. Until you connect a tracker, Probe behaves
exactly as before and just hands you the report.

## Frequently asked questions

**Do I need to change my test plans?**
No. Existing plans run unchanged on 2.0. Automatic ticket filing is the
only thing that needs a one-time integration setup.

**What if Probe files a ticket for something that is not a bug?**
Flake-aware retries are designed to prevent exactly that. A failure is
only filed if it reproduces in a clean session. If something still slips
through, closing the ticket teaches the agent for that workspace.

**Does 2.0 cost more?**
No. Per-step perception is cheaper, and parallel runs reuse the same
budget. Pricing on every plan is unchanged.

**Which trackers are supported?**
Linear, Jira, and GitHub Issues at launch. More are coming based on what
customers connect most.
